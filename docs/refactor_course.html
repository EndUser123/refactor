What is the refactor Package?

A multi-file refactoring orchestrator with rollback safety nets

The Core Problem It Solves

When you refactor a complex Python codebase — renaming a function across 30 files, extracting a class, restructuring imports — you face three risks:

1
Missed files

Grep-based replacements miss files or get the pattern wrong

2
No way back

When something breaks, you have no clean rollback path

3
Broken tests

Changes pass grep but fail at runtime or in test suites

💡
Key Insight

The refactor package treats refactoring like surgery — it plans the cut, verifies the incision site, makes the change, and confirms the patient survived before moving to the next file.

A Typical Refactoring Session

Here's what happens when you invoke the /refactor skill on a directory:

1
Scan the codebase

Discovers all Python files, finds import/export relationships

2
Build a refactor plan

Maps out which files change, in what order, with what constraints

3
Execute with TDD discipline

Runs tests before and after each file change — if tests fail, rollback triggers

4
Persist state

Tracks progress so you can resume mid-session if interrupted

The Planning File

Before making any changes, refactor_plan.py generates a plan file that documents what will change and why:

CODE 
# Generated plan for multi-file refactor
changes = [
  {
    "file": "src/auth.py",
    "action": "rename",
    "symbol": "verify_token",
    "new_name": "validate_jwt",
    "line_range": [45, 67],
  },
  {
    "file": "src/gateway.py",
    "action": "update_import",
    "from": "auth.verify_token",
    "to": "auth.validate_jwt",
  },
]
PLAIN ENGLISH

This is the plan — a list of every change to be made, with file paths and line numbers so nothing is missed.

Each change is explicit: rename this symbol, update that import, on this line range.

Having the plan upfront means you can review it before any code is touched — and debug it if something goes wrong.

💡
Why a Plan File?

Without a plan, a refactor is just a sequence of edits. With a plan, it's a verifiable process — you can check the plan before running, check the plan against actual changes, and rebuild from the plan if something breaks.

📋

⚡

Scaffolds pytest tests for the refactored code to verify behavior is preserved across all modified files.

How CodeScanner Maps the Codebase

The CodeScanner builds a symbol graph — a map of every function, class, and import and where they live:

CODE 
class CodeScanner:
    def scan(self, root: Path) -> SymbolGraph:
        files = list(root.rglob("*.py"))
        symbols = {}
        for f in files:
            tree = ast.parse(f.read_text())
            for node in ast.walk(tree):
                if isinstance(node, ast.FunctionDef):
                    symbols[node.name] = {
                        "file": str(f),
                        "line": node.lineno,
                    }
        return SymbolGraph(symbols)
PLAIN ENGLISH

Walk through all .py files in the project, parse each one into an AST (Abstract Syntax Tree)

Visit every node in the tree — when you find a function definition, record its name, which file it's in, and what line it starts on

Return a symbol graph — essentially a dictionary where any symbol name maps to its location

This gives you the full map before you start making changes

Synergy Detection — Finding Related Changes

The SynergyDetector goes beyond simple symbol mapping. It finds cross-file patterns — when two files both call a function you're about to change, or when a refactor in one file implies a related change in another:

💡
DRY Violations and Synergy

DRY means "Don't Repeat Yourself." When code appears in multiple places and you change one but not the others, you get inconsistency. The SynergyDetector finds these repeated patterns so the refactor can fix all of them at once.

1
Cross-file pattern matching

Detects when the same logic appears in multiple files

2
Dependency chain tracking

Follows import chains to find indirect callers

3
Refactor propagation

Suggests extending a change to all synergy-linked locations

The StateManager — Persistence Between Sessions

The StateManager persists progress to disk so a refactor can survive terminal restarts:

CODE 
class StateManager:
    def save(self, state: RefactorState):
        path = self.state_file()
        with open(path, "w") as f:
            json.dump(state.to_dict(), f)
        lock_path = path.with_suffix(".lock")
        lock_path.write_text(str(os.getpid()))

    def load(self) -> Optional[RefactorState]:
        path = self.state_file()
        if not path.exists():
            return None
        return RefactorState.from_dict(json.load(open(path)))
PLAIN ENGLISH

Save the current refactor state (which files are done, what's next) as JSON to a state file

Also write a lock file with the process ID — this prevents two terminals from running the same refactor simultaneously

When loading, if the state file doesn't exist, return None (no in-progress refactor)

If it exists, reconstruct the RefactorState from the saved JSON

Inter-Process Safety

💡
Why the Lock File?

Two terminals both loading "the same refactor session" would corrupt state — both would think they're in charge and both would write to the same file. The lock file with the PID means a new terminal can detect "there's already a refactor running under PID X" and refuse to start a second one.

The Clever Patterns

How complexity triage, rollback, and test scaffolding work

ComplexityTriage — Risk-Based Prioritization

Not all files are equal risk. ComplexityTriage scores each file by cyclomatic complexity — essentially, how many decision points does this code have?

HIGH
High complexity files

Refactor first — catch problems while you still have context

MED
Medium complexity files

Refactor once the high-risk ones are verified

LOW
Low complexity files

Last — these are low risk and often done as a batch

The TDD Loop — Red, Green, Refactor

For each file change, the executor runs a three-phase loop:

🔴
RED

Take a snapshot (git commit), run existing tests — confirm they pass before touching anything

🟢
GREEN

Apply the change, run tests — they must pass or the change is rejected

🔵
REFACTOR

Keep the passing tests, commit the change, move to the next file

RollbackManager — Git-Based Safety Nets

CODE 
class RollbackManager:
    def snapshot(self, file: Path) -> CommitHash:
        result = run("git add", file)
        result = run("git commit -m", f"SNAPSHOT: {file.name}")
        return result.stdout.strip()

    def rollback(self, hash: CommitHash):
        run("git reset --hard", hash)
PLAIN ENGLISH

Before touching any file, stage it and commit it with a "SNAPSHOT" label — this is your restore point

If tests fail, reset to that snapshot — the file goes back to exactly how it was before you touched it

Git handles all the storage — no custom backup files needed

When Things Break

Debugging intuition and common failure modes

Common Failure Scenarios

⚠️

Import graph mismatch

A symbol is renamed in file A but not in file B's import statement — runtime ImportError. This is caught by the test suite in the GREEN phase.

🔗

Circular dependencies

Moving a function to a new module creates an import cycle — the new module imports something that imports it back. PlanReview catches this before execution.

📝

State desynchronization

The state file records file 3 as "done" but file 2 actually failed — if you resume, file 2 is skipped and the gap propagates. Lock files prevent concurrent runs.

Find the bug in this state file handling code:
